# Honors & Accomplishments: Evidence-Led Page Strategy

## Executive recommendation

Create an evolving **Recognition Record** at `/honors-service`, not a trophy wall. The page should give a reviewer three answers within one minute:

1. What did Aarti earn or advance through?
2. Who recognized it, when, and at what level?
3. What problem, project, or contribution sits behind that recognition?

The page now includes an editable `RecognitionLedger` Puck block. Its records are filterable and carry structured fields for the recognition title, issuer, year, location, category, project context, verification state, and evidence URL. Adding a future accomplishment is an editorial task in Puck or `content/pages/honors-service.json`; it does not require a new layout or a code change.

## Important framing: ambition without an unsupported claim

The public record supports a strong story: Aarti is earning meaningful recognition for mathematics, coding, science-fair inquiry, and tools intended to help students. It does **not** support a claim that she is “well on her way to a Nobel Prize.” The Nobel Prizes do not include dedicated categories for AI, innovation, mathematics, or problem-solving; and future awards cannot be predicted responsibly.

Use this framing instead:

> Aarti is building an early, evidence-led record of mathematical inquiry, responsible AI exploration, student-centered software, and community-minded problem solving. Recognition is presented as a signal of work already completed—not a promise about future prizes.

This is both more modest and more convincing. Nobel laureate biographies themselves tend to connect distinctions to a longer arc of work, collaborators, and social purpose rather than presenting awards as self-contained proof of future greatness. See [Anne L’Huillier’s biographical record](https://www.nobelprize.org/prizes/physics/2023/lhuillier/biographical/) and [Stanley Prusiner’s record](https://www.nobelprize.org/prizes/medicine/1997/prusiner/biographical/).

## Design specification

### Page hierarchy

```text
Hero: concise thesis + no inflated claims
  ↓
Recognition Record: filterable, evidence-linked award ledger
  ↓
Method: how entries are verified and maintained
  ↓
Work behind the recognition: project cards / repository links
  ↓
Community and service context
  ↓
Future direction: inquiry questions, not future-prize prediction
```

### Recognition card anatomy

Every record uses the same fields:

| Field | Required | Reason |
| --- | --- | --- |
| Recognition title | Yes | Gives a reviewer the precise signal. |
| Issuer | Yes | Identifies who made the recognition. |
| Year | Yes | Creates a credible chronology. |
| Location / level | Recommended | Establishes context without inflating selectivity. |
| Category | Yes | Enables filtering as the archive grows. |
| One-sentence recognition description | Yes | States the result precisely. |
| Project context | Recommended | Shows the work behind the honor. |
| Evidence URL and label | Required for `Documented` status | Makes verification one click away. |
| Verification state | Yes | Prevents a draft, self-reported, or vague entry from appearing fully verified. |
| Editorial note | Optional | States limits, pending details, or source caveats. |

### Visual and editorial rules

- Use award icons and restrained emphasis—not trophy imagery, confetti, rank badges, or inflated superlatives.
- Lead with an action or project where relevant; place award names in the supporting hierarchy.
- Use exact placement wording: “won,” “received,” “advanced,” “finalist,” “participant,” or “selected” only as supported by evidence.
- Link to the awarding organization or official winner list before linking to a press story.
- Do not quote judge feedback unless permission and attribution are available.
- Do not publish certificates that reveal student ID numbers, signatures, home address, date of birth, QR codes, or private contact information.
- Ensure each external link opens safely and is understandable from its link text.

## Maintenance workflow

### Before publication

1. Save the certificate, official winner list, school announcement, or organizer email in a private evidence folder.
2. Record the exact award title, issuer, date, project, level, and public URL.
3. Decide whether the evidence may be shared publicly.
4. Write a 30–60 word description that states only what the evidence establishes.
5. Have an adult reviewer confirm the public wording when the record involves school, competition, media, or a minor’s personal information.

### Add an entry in Puck

1. Open `/admin/edit/honors-service`.
2. Select **Recognition Ledger**.
3. Add a record using the structured fields.
4. Choose `Documented` only when an official public source has been added.
5. Preview on mobile and desktop; verify the link and spelling.
6. Save, then run the normal quality checks before deploying.

### Content governance states

| State | Public treatment |
| --- | --- |
| Evidence collected, not public | Keep private; do not publish. |
| Official public source available | Publish as `Documented` with source link. |
| Award confirmed but public source not yet available | Hold it, or publish only after the adult reviewer approves a “source forthcoming” note. |
| Participation or submission only | Put it in a project timeline, not the honors ledger, unless it is formally recognized. |
| Duplicate coverage | Keep one record; attach multiple evidence links only if they add meaningful verification. |

### Phase 3 — As new recognition arrives

- Add entries at the moment evidence is received.
- Preserve the same field structure and avoid retroactive rewriting that erases original context.
- Add a yearly timeline only after at least two verified entries per year make it useful.
- Add a “Selected recognition” summary on the homepage only after the ledger has enough material to remain current.

### Phase 4 — Long-term credibility

- Request permissioned mentor, teacher, or judge context only where it adds a specific factual perspective.
- Track community-oriented outcomes separately from awards: usability feedback, collaborators, public adoption, or educational artifacts.
- Publish a short annual “what I learned” reflection that distinguishes evidence, open questions, and future work.

- [ ] Each project statement is specific and does not overstate outcome or validation.
- [ ] The page contains no prediction of awards or future status.
- [ ] New entry creation works in Puck without code changes.
- [ ] Mobile filters, keyboard focus, link labels, and reduced-motion behavior are checked.
- [ ] The resulting portfolio story remains about useful work for people, not a list of trophies.
